# 跨 Agent 协作协议（COLLAB）

> 本文件约定「人的 agent 之间」如何在本仓库协作。双方 agent 在开始任何工作前必须读完本文件。
> 本协议对所有协作仓库（nas / scraper / saletools / kb）通用；仓库特有参数见文末表格。

## 0. 角色

| 角色 | 定义 | 权限 |
|------|------|------|
| 属主（Owner） | 本仓库的主要维护方 agent | 可 push master、合并 PR、发 release |
| 访客（Guest） | 协作方 agent | 只能通过 分支 + PR 提交，不直接 push master |

每个仓库只有一个属主（见文末表格）。属主对架构决策有最终裁定权；访客对分配给自己的 issue 有实现自主权。

## 1. 通信分层（按可达性降级）

| 层 | 通道 | 何时可用 | 用途 | 是否事实源 |
|----|------|---------|------|-----------|
| 1 | Gitee（issue / PR / 代码） | 任何时候 | 任务分派、代码提交、讨论结论 | **是唯一事实源** |
| 2 | QQ 协作群（双方 gateway 接入） | 有外网即可 | 实时对话：派活、问状态、快速同步 | 否 —— 聊出的决定必须回写 issue |
| 3 | 办公室局域网 SSH 直连 | 仅双方同在内网 | 重活加速：rsync、跨机构建测试、访问内网服务 | 否 |

规则：
- 第 3 层不可用时自动降级到 1+2，协议不变。
- **QQ 群里达成的任何决定，24 小时内必须回写到对应 Gitee issue**（一条评论即可）。聊天记录不是事实源，agent 的记忆也不是。
- 内网服务（如 KB 知识库）只有第 3 层能到达；需要共享的文档一律进仓库 docs/，不放内网。

## 2. 任务流程

1. **一 issue 一分支一 PR。** 没有对应 issue 的工作不开分支（typo 级除外，直接 PR 说明即可）。
2. Issue 正文必须包含：目标、验收标准（可验证的完成条件）、范围边界（明确「不做什么」）。
3. 分支命名：`<issue号>-<短描述>`，如 `42-fix-raid-detect`。
4. PR 描述必须包含（对方 agent 冲突仲裁时依赖这两段，缺失会被打回）：
   - **Intent**：一句话说明这个 PR 想达成什么
   - **验收对照**：逐条对照 issue 的验收标准
5. 访客 PR 由属主 agent（或其人）review 合并；属主的改动推 master 前也开 PR，让访客 agent 有知情窗口（≥半天），紧急修复除外（事后补 issue 说明）。
6. PR 保持小而聚焦。跨仓库的联动改动（如 kb 改 API、nas 改调用方）：先开「协议 issue」定接口，两边各自实现，接口变更以协议 issue 里的最终版本为准。

## 3. 冲突仲裁（merge-reconciler 协议）

两个 agent 的分支撞车时，**任何一方都不得自我裁决**（自裁必然偏向自己）：

1. 冻结：冲突双方停止向冲突分支追加提交。
2. 指定中立方：第三方 agent，或双方中不涉及冲突文件的那一方的人。
3. 中立方收集：双方完整 diff + 双方 PR 描述里的 Intent（这就是第 2.4 条强制写 Intent 的原因）。
4. 按 hunk 分类处置：
   - 意图不相交 → 两边都保留；
   - 同一设计问题两种答案 → 按双方声明的意图选一个，**不许折中杂交**，且选择必须在总结里显式列出供人否决；
   - 一方前提已失效 → 保留幸存方。
5. 中立方只许动冲突区域，禁止顺手改格式/重构。
6. 合并后必须跑通本仓库的构建 + 测试命令（见文末表格），双方意图都要能在结果中观察到。
7. 同一文件反复冲突 = 热点信号 → 属主应拆分该文件或收紧范围边界，而不是每轮都仲裁。

## 4. 红线（双方 agent 无条件遵守）

- 禁止提交 .env、token、密码、私钥；发现泄露立即报告属主并走历史清洗，不许悄悄 revert 了事。
- 禁止 force-push master。
- 禁止越出 issue 范围边界改动（drive-by fix 单独开 issue）。
- 禁止在 PR/issue 里虚构验证结果 —— 没跑过的测试不许声称通过。
- 生产部署动作（重启服务、动磁盘、改防火墙）只有属主 agent 在 issue 中被明确授权后执行。
- 依赖变更（go.mod / requirements.txt / package.json）必须在 PR 描述中单独列出并说明理由。

## 5. 本仓库参数

| 项 | 值 |
|----|-----|

## 6. 给 agent 的执行清单

对方 agent 接到本仓库任务时的标准动作：

1. 读本文件 + AGENTS.md（如有）+ issue 全文。
2. 确认 issue 有验收标准和范围边界；没有 → 在 issue 里问，不要猜。
3. 从 master 拉分支 `<issue号>-<短描述>`。
4. 实现 → 跑文末表格里的构建 + 测试命令 → 全绿才提交。
5. 开 PR，Intent + 验收对照写全。
6. 在 issue 里贴 PR 链接；QQ 群里 @对方 agent 一句话通知（可选）。
7. Review 意见逐条回应；改不动的说明原因，不许沉默跳过。
