# CMDB 凭证保险箱 & 密码生成器 — 设计参考

> **适用场景**：任何需要安全存储用户个人凭证（API Key、平台密码等）的 Web 系统。
> **核心技术**：零知识加密（Zero-Knowledge Encryption），服务器永不接触明文。

---

## 一、凭证保险箱

### 1.1 核心原则

> **服务器永远看不到明文。管理员也看不到别人的密码。**

加密/解密全部在浏览器端完成（Web Crypto API），服务器只存储密文。任何人（包括数据库管理员）都无法查看他人的凭证内容。

### 1.2 架构图

```
┌─ 浏览器端（用户 A）──────────┐    ┌─ 服务器端 ─────────────────┐
│                               │    │                             │
│  保险箱口令（用户记忆）         │    │  salt                     │
│       ↓                       │    │  verification_hash         │
│  MasterKey = PBKDF2(口令,salt) │    │  encrypted_data（密文）     │
│       ↓                       │    │  metadata（明文：平台名等）  │
│  SHA-256(MasterKey) → 发往服务器│──→│  比对 verification_hash     │
│       ↓                       │←──│  验证通过，返回密文          │
│  AES-256-GCM 解密              │    │                             │
│       ↓                       │    │                             │
│  明文显示给用户                 │    │                             │
└───────────────────────────────┘    └─────────────────────────────┘
```

### 1.3 加密细节

| 环节 | 算法 | 说明 |
|------|------|------|
| 密钥派生 | PBKDF2 (SHA-256, 600,000 次迭代) | Web Crypto API 原生支持 |
| 加密 | AES-256-GCM | 认证加密，防篡改 |
| IV | 每次加密随机生成 12 字节 | 存在 ciphertext 前面 |
| 密文格式 | `base64( IV(12B) + ciphertext + auth_tag(16B) )` | 标准 GCM 格式 |
| 验证 | `SHA-256(raw_key)` 与服务器 `verification_hash` 比对 | 服务器不知道口令 |

### 1.4 数据模型（3 张表）

#### credential_vault_user — 用户保险箱设置

| 字段 | 类型 | 说明 |
|------|------|------|
| id | SERIAL PK | |
| user_id | INTEGER UNIQUE FK → 用户表 | 每人一条记录 |
| salt | BYTEA | 随机盐 |
| verification_hash | BYTEA | SHA-256(派生密钥) |
| iterations | INTEGER DEFAULT 600000 | PBKDF2 迭代次数 |
| locked | BOOLEAN DEFAULT TRUE | 是否锁定 |
| failed_attempts | INTEGER DEFAULT 0 | 连续失败次数 |
| locked_until | TIMESTAMPTZ | 锁定到期时间 |

#### credential_entry — 加密凭证条目

| 字段 | 类型 | 说明 |
|------|------|------|
| id | SERIAL PK | |
| user_id | INTEGER FK → 用户表 | 归属用户 |
| platform_name | VARCHAR(200) | **明文**：平台名（阿里云/华为云/GitLab...） |
| category | VARCHAR(100) | **明文**：分类（cloud/idc/database...） |
| tags | TEXT[] | **明文**：标签 |
| encrypted_data | BYTEA | **AES-256-GCM 密文**（解密后为 JSON） |
| url | TEXT | **明文**：平台网址 |
| notes_preview | VARCHAR(100) | **明文**：备注摘要（不含敏感信息） |

**encrypted_data 解密后的 JSON 结构：**
```json
{
  "username": "admin@example.com",
  "password": "***",
  "api_key": "***",
  "secret_key": "***",
  "notes": "生产环境主账号"
}
```

#### credential_audit_log — 审计日志

| 字段 | 类型 | 说明 |
|------|------|------|
| id | SERIAL PK | |
| user_id | INTEGER FK → 用户表 | |
| action | VARCHAR(30) | unlock / lock / view / create / update / delete |
| entry_id | INTEGER NULL | 操作的条目 |
| ip_address | VARCHAR(45) | |
| user_agent | TEXT | |

### 1.5 API 设计（11 个端点）

| 方法 | 路径 | 用途 |
|------|------|------|
| GET | `/api/v1/credential/vault-status` | 查询保险箱状态 |
| POST | `/api/v1/credential/setup` | 首次设置口令 |
| POST | `/api/v1/credential/unlock` | 解锁（验证口令） |
| POST | `/api/v1/credential/lock` | 锁定 |
| PUT | `/api/v1/credential/change-passphrase` | 修改口令（重加密所有条目） |
| GET | `/api/v1/credential/entries` | 列表（仅 metadata） |
| GET | `/api/v1/credential/entries/{id}` | 获取单条密文 |
| POST | `/api/v1/credential/entries` | 创建条目 |
| PUT | `/api/v1/credential/entries/{id}` | 更新条目 |
| DELETE | `/api/v1/credential/entries/{id}` | 删除条目 |
| GET | `/api/v1/credential/audit-log` | 审计日志 |

**服务端安全强制措施：**
- 所有查询 `WHERE user_id = current_user_id`，admin 也不例外
- 解锁接口限流：5 次失败 → 锁定 30 分钟
- 审计日志记录所有操作（不含敏感数据）

### 1.6 前端交互流程

#### 首次使用
1. 用户点击「🔐 凭证保险箱」→ 显示设置引导
2. 输入保险箱口令（确认两次，独立于登录密码）
3. 浏览器生成 salt → 派生密钥 → 计算 verification_hash
4. 发送 salt + verification_hash 到服务器
5. 保险箱创建成功，自动解锁

#### 日常使用
1. 点击「🔐 凭证保险箱」→ 弹出解锁框
2. 输入口令 → 浏览器派生密钥 → 发送 verification_hash 验证
3. 验证通过 → 显示凭证列表（平台名 / 分类 / 用户名掩码)
4. 点击查看 → 浏览器解密 → 显示明文（**15 秒后自动遮罩**）
5. 复制密码 → **30 秒后自动清除剪贴板**
6. **15 分钟无操作 → 自动锁定**

#### 修改口令
1. 验证旧口令 → 获取所有条目 → 逐条重加密 → 提交服务器
2. 浏览器端 `deriveKey(oldPwd)` 验证，`deriveKey(newPwd)` 生成新密钥
3. 服务端在一个事务中更新 salt + verification_hash + 所有 encrypted_data

### 1.7 安全措施总览

| 措施 | 说明 |
|------|------|
| 🔒 零知识 | 加密/解密全在浏览器，服务器只有密文 |
| 🚫 管理员隔离 | admin 通过 DB 只能看到密文，无法解密 |
| 🔑 独立口令 | 保险箱口令 ≠ 登录密码 |
| ⏱️ 自动锁定 | 15 分钟无操作自动锁定 |
| 🛑 暴力破解 | 5 次失败 → 锁定 30 分钟 |
| 📝 完整审计 | 所有操作记录到 audit_log |
| 🔗 行级安全 | 服务端 `WHERE user_id = :current_user_id` |
| 🧹 剪贴板清理 | 复制后 30 秒自动清除 |
| 🚫 无恢复 | **忘记口令 = 数据永久丢失**（首次设置时明确告知） |

## 二、密码生成器

### 2.1 概述

使用 `crypto.getRandomValues()`（Web Crypto API）生成安全随机密码，零外部依赖，完全在浏览器运行。

### 2.2 两种形态

| 形态 | 位置 | 用途 |
|------|------|------|
| **凭证表单内嵌** | `credential-vault.js` 内部 | 新增/编辑凭证时，密码字段旁的「🔑 生成密码」按钮弹出弹窗 |
| **独立工具页面** | `static/js/password-generator.js` (172 行) | 侧边栏独立入口，不依赖保险箱解锁 |

### 2.3 核心算法

```
1. 确定字符池：从 {大写, 小写, 数字, 符号} 中已选类型拼接
2. 用 crypto.getRandomValues() 生成随机字节
3. 前 N 位确保每类字符至少出现 1 次
4. 剩余位从全字符池随机填充
5. Fisher-Yates 洗牌打乱顺序
```

### 2.4 功能配置

| 参数 | 默认值 | 范围 |
|------|--------|------|
| 长度 | 16 | 8-64 |
| 大写字母 A-Z | ✅ 开启 | 可关闭 |
| 小写字母 a-z | ✅ 开启 | 可关闭 |
| 数字 0-9 | ✅ 开启 | 可关闭 |
| 特殊符号 !@#$... | ✅ 开启 | 可关闭 |

### 2.5 独立工具页面额外功能

- **六档强度指示器**：根据字符多样性和长度实时评估
- **生成历史**：最近 20 条，可回看和复制
- **复制按钮** + Toast 提示
- 不依赖保险箱解锁状态，任何人可直接使用

## 四、复用指南

### 如果要在你的系统中实现凭证保险箱

1. **数据表**：复制上述 3 张表结构，将 `user_id` 改为你的用户表 FK
2. **后端 API**：186 行 `credential.py`，核心是 `WHERE user_id = :current_user_id` 的行级安全
3. **前端 JS**：931 行 `credential-vault.js`，所有加密逻辑都在里面，可直接复用
4. **关键决策点**：
   - PBKDF2 迭代次数（当前 600,000，平衡安全与性能）
   - 自动锁定时间（当前 15 分钟）
   - 失败锁定阈值（当前 5 次/30 分钟）

### 如果只要密码生成器

直接复制 172 行 `password-generator.js`，无后端依赖，独立运行。

### Pydantic v2 bytes→base64 转换（FastAPI 特有）

```python
from pydantic import BaseModel, field_validator
import base64

class CredentialEntryFull(BaseModel):
    encrypted_data: str

    @field_validator('encrypted_data', mode='before')
    @classmethod
    def bytes_to_base64(cls, v):
        if isinstance(v, bytes):
            return base64.b64encode(v).decode()
        return v

    class Config:
        from_attributes = True
```

## 五、与常见方案对比

| 方案 | 服务端可见明文 | 管理员可偷看 | 跨设备同步 | 忘记密码恢复 |
|------|:---:|:---:|:---:|:---:|
| **本方案（零知识）** | ❌ | ❌ | 天然支持（密文在 DB） | ❌ |
| 服务端加密存储 | ❌ | ✅ admin 可解密 | ✅ | ✅ |
| 明文存储 | ✅ | ✅ | ✅ | ✅ |
| 第三方密码管理器 | ❌ | ❌ | 依赖服务 | 依赖服务 |

> **本方案的核心取舍**：用「无法恢复」换取「任何人不经用户同意都无法访问」。如果你的场景需要密码恢复功能，此方案不适用。
