# 存储 → 目录 → 用户 权限模型梳理与讨论

> 最后更新: 2026-09-03
>
> 目的: 梳理「用户 ↔ 共享文件夹 ↔ 协议」权限这条线的现状、已修复项、核心难点与待决策点，供团队一起讨论确定后续方案。

---

## 一、我们到底想要什么

一句话: 给每个用户、对每个共享文件夹、通过每种协议，都能精确控制「能不能访问、能读还是能写」。

理想模型是三维矩阵:

```
用户 × 文件夹 × 协议 → 访问权限（禁止 / 只读 / 读写）
```

用户管理里已经有一个「权限矩阵」页面，UI 上就是按这个三维设计的——每个单元格可选「读写 / 只读 / 禁止」。但后端数据模型和协议本身都跟不上这个 UI，这是所有问题的总根源。

---

## 二、现状（数据模型 + 各协议真实能力）

### 数据模型

`folders.db` 的 `folders` 表是「文件夹级」的:

```
每个文件夹 = 一个 valid_users 白名单 + 一个 permission（读写/只读/禁止）
```

注意: `permission` 是「每文件夹一个值」，不是「每用户一个值」。所以数据模型本身就表达不了「A 读写、B 只读」这种用户级差异。

### 各协议真实能做到的

| 协议 | 按用户白名单 | 按用户读写粒度 | 说明 |
|------|:---:|:---:|------|
| SMB | ✅ | ❌ | 唯一有白名单的协议。`valid users` 控制谁能连；`read only` 是共享级开关（整组一起只读，不能分人）。已补 `force user/group` 让白名单用户能真正写进目录。 |
| NFS | ❌ | ❌ | 网段级导出，无按用户概念（协议本质如此，改不了）。 |
| FTP | ❌ | ❌ | vsftpd 把用户 chroot 到 `/data/private/$USER`，共享文件夹根本不通过 FTP 暴露；userlist 是白名单模式。 |
| WebDAV | ❌ | ❌ | `rclone serve webdav /data` 单一全局凭据（fm），不认每文件夹、每用户权限。 |
| S3 | ❌ | ❌ | 同上，`rclone serve s3 /data` 单一全局 auth-key。 |

**结论**: 真正有「按用户 × 按文件夹」隔离的，目前只有 SMB 一个协议，而且 SMB 也只是「谁能访问」这一维，读写粒度还是共享级的。

---

## 三、已修掉的可运行项（已部署）

1. 创建用户时 Samba 从未真正启用 —— 现在会 `smbpasswd -a` 带密码加入。
2. SMB 托管共享缺 `force user/group` + `create mask`，导致白名单用户写不进目录 —— 已对齐模板。
3. NFS 硬编码 `192.168.0.0/16` 网段 —— 已改为自动检测局域网网段。
4. FTP userlist 白名单逻辑写反（enable 成了移除、disable 成了加入）—— 已按白名单语义修正。
5. smb.conf 托管段重复 START 标记 —— `replaceManagedBlock` 已幂等化。
6. 权限矩阵直接改 smb.conf、绕过元数据、会被下次配置同步冲掉 —— 已改为走元数据 + 统一重生成。

这 6 项解决的是「能跑通、能被正确覆盖」的 bug，但没解决「按用户粒度」这个核心难题。

## 四、核心难点（卡点）

### 难点 1：数据模型是文件夹级，不是用户级
一个文件夹只有一个 `permission`。要做「A 读写、B 只读」，元数据必须从「文件夹级 permission」改成「用户 × 文件夹 权限表」，这是 schema 级重构，前端权限矩阵、后端生成引擎、各协议落地全都要跟着动。

### 难点 2：SMB 的按用户只读需要 `read list` / `write list`
Samba 本身支持 `read list` / `write list` 按用户区分读写，这是唯一不用换服务的路径。但要接上，就得先把上面的元数据模型改出来，二者绑在一起。

### 难点 3：FTP 无解（在当前 vsftpd 下）
vsftpd 无论真实用户还是虚拟用户，都是「一个用户一个 chroot 根」，做不到「一个用户访问多个文件夹」，`write` 权限也是按用户不是按目录。要真矩阵只能换 proftpd（mod_auth_file）或 pure-ftpd——换服务，不是加配置。

### 难点 4：WebDAV / S3 是全局服务
`rclone serve` 用单一凭据暴露整个 `/data`。要按文件夹隔离，得每文件夹起独立实例（依赖「多实例端口可配置」这个 TODO），或者换支持 ACL 的服务。

### 难点 5：文件属主的一致性
SMB 现在用 `force user = nasUser`，文件都归 nasUser。将来如果 FTP 用虚拟用户写、WebDAV 换实例写，属主会分裂成多个，需要统一属主策略，否则同一文件夹里 SMB 写的文件和 FTP 写的文件权限打架。

### 难点 6：界面徽标在「夸大」覆盖
现在 `isFTPAccessible` 之类只判断「服务在跑」，就给每个文件夹打 FTP✓ / DAV✓ / S3✓，实际那个文件夹根本不可达。要么按真实可达性显示，要么明确标成「全局服务」，否则误导用户以为已经按用户隔离了。

## 五、待决策点（供讨论）

1. **范围**: 家用 NAS 到底需不需要「按用户的读写粒度」？还是「谁能访问 + 整文件夹统一读写」就够？这决定难点 1、2 值不值得做。如果不需要，权限矩阵 UI 的「只读」选项就该砍掉或降级，避免误导。

2. **分期**: 是否接受「SMB 先做到按用户、FTP/WebDAV/S3 明确标成全局访问」？还是所有协议必须一次性对齐？

3. **FTP 方向**: 保留 vsftpd（只做私有目录）、上虚拟用户（一人一目录）、还是换 proftpd 做真矩阵？

4. **元数据重构范围**: 新建「用户×文件夹」权限表，还是在 `folders` 表上加 `read_list`/`write_list` 字段？
