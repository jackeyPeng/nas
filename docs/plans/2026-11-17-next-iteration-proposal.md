## 二、本轮盘点新发现（应优先处理的实抓缺陷与欠账)

1. **注册表不自动刷新（实测缺陷，半天级修复）**
   `.48/.57` 建池后 `GET /api/system/check`（默认无 action）只回读 registry.db 旧快照，出现「安装时 41/41，建池后回读仍 32 pass + 9 warn」的自相矛盾，用户会以为系统坏了。只有显式 `?action=refresh` 或 AI 读工具才真重算。
   修法方向: ①建池/删池/出厂重置/共享 CRUD 落库后同异步触发 `RefreshRegistry()`（或给 GetRegistry 加 TTL/基于磁盘操作代际的失效标记，避免面板每读一次就跑 41 项检查）；②速赢方案：向导/池操作 done 事件里调用一次 RefreshRegistry 即可消除 95% 场景。属 S2「完成必须由内核状态复核」原则的注册表层缺口。

2. **S2 磁盘操作安全残项**（diskmgmt 共识审查遗留，见 TODO 与 opencode/consensus 报告）:
   - handlePoolDelete 的 confirm 校验仍没接 canWipe 统一闸门/wipefs 前无系统盘复核断言（beta.34 做了大半，复查补尾）
   - GET 触发的破坏性 SSE 接口（reset-stream 等）改 POST 的评估未做
   - diskmgmt 语句覆盖率仍低（~15%+，写路径 handlePoolExtendStream/handleRAIDExpandStream 无测试）

3. **文档债已还清**（本轮）: 协议默认/A1 门禁/密码 8 位口径同步至 checklist/协议详解/产品手册；§八#2 全局协议旁路以手册 §8.5 收口。

## 四、建议执行顺序（待拍板）

1. **快修轮（先做，1-2 天）**: 注册表自动刷新根修 + 补 diskmgmt 写路径几条关键测试（handlePoolExtendStream/handleRAIDExpandStream 正反用例）。小而确定，直接消掉验收口径被破的矛盾。
2. **主线 A（本轮主体，1-2 周）**: #37 外部应用注册机制 + 安康 M4 迁入。理由: 有既定拍板和真实用户；做完后「NAS 承载家庭应用」有了第一个样板；监控/告警/备份能力顺带被真实负载检验。产出物: external-apps 模块（注册 CRUD + 门户卡 + healthz 纳管 + 防火墙联动）、安康部署迁移、验收套件新增断言。
3. **穿插 C**: #12 照片备份切片（pwa + filemgmt 复用，与主线 A 无耦合，可作两台机的用户级验收素材）。
4. **B 立设计文档，不写代码**: AI M3 先出设计稿（工具域边界 + 隐私模型 + 验收标准），过审后排期。
5. **D 并行不阻塞**: Z1 Lite 结构评审（零成本）、备货/定价等商业动作等用户另行启动。
6. **冻结**: 硬件定价、free/Plus/Enterprise 分层。
