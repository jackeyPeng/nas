# M1 实施计划：托管应用核心（无基座服务版）

> 依据 docs/APP-SPEC.md v0.1 与 docs/plans/2026-11-20-app-platform-design.md
> 目标：master 线落地「装一个托管应用全链路」，基座服务（PG/Valkey/MQTT）留 M2
> M1 中 manifest 的 pgsql/cache/mqtt/requires 声明 → 校验器返回明确错误「该能力 M2 提供」

## 任务切片（顺序执行，每片独立可测）

1. **契约层**（web/modules/apps/）
   - manifest.go：结构体 + 严格校验（未知字段拒绝、id 规则、semver、port 范围、permissions 枚举）
   - package.go：tar.gz 解包（路径穿越防护）、布局校验（manifest/icon/app/unit.tpl）
   - sign.go：ed25519 验签；scripts/appsign.go 或 tools/ 生成密钥对与 detached sig（开发密钥对入仓 testdata，公钥常量先留注入位）
   - 单测全覆盖（含恶意包用例：路径穿越/未知字段/坏签名/缺文件）

2. **注册与生命周期**（web/modules/apps/）
   - registry.go：SQLite（apps.db）记录已装应用、端口占用表（18000-18999 分配）
   - lifecycle.go：install（两步确认）→ 系统用户 nasapp-<id>、目录、unit 模板渲染（模板变量注入 + 核心硬化指令强制合并）→ start/stop/restart/upgrade（旧程序目录备份+失败回滚）/uninstall（keepData）
   - 全部走既有 sudo 白名单模式扩展（SudoExec），sudoers 片段新增命令白名单最小化
   - API 挂 /api/apps/*，管理员权限中间件复用

3. **反代与 SSO**
   - proxy.go：/apps/<id>/ 前缀反代（http.ReverseProxy，本机端口）、转发前会话校验（401 语义）、X-NAS-User/X-NAS-Auth（HMAC-SHA256，±60s 容差）注入
   - 安装时为应用生成专属 secret 注入 unit（Environment）
   - 单测：header 签名/验签往返、未认证 401、前缀透传

4. **健康纳管**
   - healthz 60s 轮询（复用 monitor 调度），连续 3 次失败产事件（走既有 events/告警链路），不自动重启
   - 注册表新增应用健康项（system_registry 挂钩）

5. **前端**（web/frontend/）
   - 应用中心页（已装卡片 + 门户入口）+ 应用详情（启停/升级/卸载/权限确认两步对话框）
   - 本地上传安装入口（市场列表 M1 末尾接 index.json 只读展示，一键安装留 M2）
   - i18n 中英两份；遵守 app.js 不膨胀约束（独立 apps.js 页面级模块，按需加载）

6. **hello-app 演示包 + 验收**
   - examples/hello-app/：最小 Go 应用（读 __PORT__/__NAS_SECRET__，验 X-NAS-Auth，/healthz，相对路径单页）
   - scripts/mkapp.sh：打包 + 签名（开发密钥）
   - 真机验收：装→确认→卡片→反代登录态→卸载留数据/清数据；acceptance-suite 新增断言
   - CHANGELOG [未发布] 段记录

## 验收口径
- go test ./... 全绿（架构边界测试更新白名单 apps→{system,monitor}）
- 两台测试机 .48/.57 真机全链路 + Chrome UI 实测
- 红线检查零命中
